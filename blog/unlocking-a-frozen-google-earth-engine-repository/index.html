Unlocking a Frozen Google Earth Engine Repository

When the GEE Code Editor stops saving and greys out every action button, the fix isn't in the browser. Force a server-side re-index from the Git CLI.

Published on August 21, 2026

At some point, a Google Earth Engine repository can lock itself out of the Code Editor. The Save button appears to work, but the next time you refresh, every change is gone. Rename and New Script are greyed out. You can still execute code in the editor — you just can’t write anything back to the server.

Signing out and back in doesn’t help. Incognito doesn’t help. Refreshing IAM roles doesn’t help. The browser isn’t the problem.

What’s Actually Going On

A GEE repository is a real Git repository. It lives on Google’s servers, exposed through the Code Editor’s UI, and backed by the same Git primitives as any other remote. When the web editor stops accepting writes, the cause is almost always at the server layer — either a stale index lock left behind by a previous operation, or the repository tripping a soft limit because of accumulated history or object size. The exact trigger varies, but the shape of the failure is always the same: the backend has stopped accepting changes and the UI has no way to force it to re-index on its own.

Before you start, rule out the obvious: confirm Git hosting isn’t down for Google’s servers, and confirm you’re actually logged into the right account in your terminal.

Back Up First

Before touching anything, make a local copy of your scripts. If the repository is already in a weird state, you want an offline snapshot regardless of how the fix turns out.

git clone https://earthengine.googlesource.com/users/YourUser/YourRepo

For Cloud Project repositories, the URL is:

https://earthengine.googlesource.com/projects/YOUR_PROJECT_ID/repos/YOUR_REPO_NAME

If Git prompts for a password, generate a fresh one at earthengine.googlesource.com/new-password and paste the authentication block into your terminal. This is a one-time token, not your Google account password.

Fix 1: Force a Server-Side Re-Index

The most reliable fix is to push a commit from the terminal. An empty commit carries no file changes, but it forces the backend to rebuild the repository’s index — which is exactly the state the editor needs to recover.

cd YourRepo
git pull
git commit --allow-empty -m "Force Unlock Repo"
git push origin master

Nothing about your scripts changes. The commit exists only to trigger the re-index.

Once the push succeeds, open the Code Editor, hard-refresh, and try saving. The Save, Rename, and New Script actions should be back.

Fix 2: Rebase, Tag, and Push a Marker File

If the empty-commit approach doesn’t take, a slightly more forceful version works by pulling the exact remote state, rebasing local changes on top, and pushing a small marker file. This writes something new into the repository, which is a stronger signal to the backend than an empty commit.

From inside your local clone:

git fetch origin
git status
git pull --rebase origin master

Then stage a small sync marker and push it:

echo "// GEE force re-index $(date)" > .GeeSync
git add .GeeSync
git commit -m "Force GEE Index Rebuild"
git push origin master

Log out of the Code Editor completely, log back in, and refresh. The repository should load cleanly.

Cleanup

Once the editor is behaving normally and your scripts are visible again, remove the marker file so it doesn’t sit in your repository forever.

git rm .GeeSync
git commit -m "Cleanup Sync File"
git push origin master

If you used the empty-commit approach, there’s nothing to clean up — an empty commit leaves no trace in the working tree.

If Neither Works

Sign out of GEE in the browser, clear site data for code.earthengine.google.com, close the tab, and sign back in. In most cases this is redundant after a successful push, but if the editor is still showing stale state after re-indexing, a full session reset forces the client to fetch the repository fresh.

Notes

This does not touch your asset data. The fix operates on the repository that stores your scripts, not on Earth Engine assets in projects/.../assets/. Images, tables, and feature collections are untouched.

References remain valid. Script IDs don’t change, so anything that imports from your repository keeps working.

Don’t run this on a shared or published repository unless you’ve coordinated with whoever else depends on it. A rebase-and-push cycle rewrites local state and can conflict with unmerged changes from other contributors.

Keep a local clone around. The single best defence against a future lock is having a working copy of your scripts outside Google’s infrastructure. If the web editor ever becomes unusable for a longer stretch, you’ll still have your code.
