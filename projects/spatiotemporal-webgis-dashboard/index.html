Street-Level Spatiotemporal WebGIS for Urban Incident Analytics

A full-stack spatiotemporal dashboard — PostgreSQL/PostGIS for spatial storage, GeoServer for layer serving, Django for the API, and OpenLayers for the front-end. Built end to end, from raw records to an interactive street-level viewport.

#WebGIS#PostGIS#GeoServer#Django#OpenLayers#Spatiotemporal#Urban Analytics

Overview

This project is a full-stack spatiotemporal WebGIS dashboard for exploring urban incident patterns at the street level. It’s not a demo — it’s a working pipeline, from data ingestion and spatial snapping through a machine learning predictor to a browser-based interface that renders thousands of street segments with dynamic time filtering, hourly pattern analysis, and year-over-year comparison.

The application is a case study: it uses a Chicago urban-incident dataset, but the architecture is general. The same stack — PostgreSQL/PostGIS for spatial storage, GeoServer for OGC-compliant layer serving, Django for API and business logic, OpenLayers for rendering — is the foundation for any street-level spatiotemporal dashboard, whether the subject is urban safety, traffic flows, service delivery, environmental monitoring, or public health.

The point of the project isn’t the dataset. It’s that a full pipeline can be built, integrated, and shipped at street granularity.

Architecture

Four layers, each with one job.

Storage — PostgreSQL + PostGIS. All incident records, street network geometry, community-area polygons, and derived prediction tables live in a single PostGIS database. Spatial indexes on street geometry allow sub-second nearest-neighbor queries at scale. PostGIS functions (ST_DWithin, ST_Distance, ST_SetSRID) do the heavy lifting for spatial joins, snapping, and proximity analysis.

Serving — GeoServer. Spatial layers are published as WMS/WFS endpoints. GeoServer sits between the database and the front-end, handling tiling, styling, and OGC-compliant queries. This decouples the map-rendering logic from the raw geometry — the front-end requests a layer, GeoServer figures out which rows to fetch, how to render them, and how to stream them efficiently.

Application — Django. Business logic lives here: the API surface that the front-end calls for filter combinations, the schedule that refreshes derived tables, and the integration point for the prediction model. Django’s ORM handles non-spatial queries; raw PostGIS calls go through psycopg2 when the query needs spatial functions the ORM doesn’t cleanly express.

Front-end — OpenLayers + Vanilla JS. OpenLayers renders the street-level vector layers over a base map, with dynamic time filtering wired into the UI. Custom D3 visualizations sit alongside the map — an hourly polar clock, a weekly calendar heatmap, a per-community bar chart, and a year-over-year trend line. No framework, no build step; the JS is written to run.

The Data Pipeline

Three Python scripts compose the pipeline. They run on a schedule — each one refreshes a specific derived table that the dashboard reads from. They’re independent, idempotent, and safe to re-run.

Script 1 — Current state. Refreshes the streetlevelcrimestoday table by truncating it and re-populating with the incident count per street for a reference day. This gives the dashboard its “today” snapshot.

cursor.execute("TRUNCATE TABLE streetlevelcrimestoday;")

cursor.execute("""
    INSERT INTO streetlevelcrimestoday (streetid, crime_count, geom, date)
    SELECT
        streets.streetid,
        COUNT(incidents.streetid),
        streets.geom,
        %s
    FROM chicagostreetsfinal_wgs84 AS streets
    LEFT JOIN incident_record ON
        ST_DWithin(streets.geom, incident_record.geom, 50)
        AND incident_record.streetid = streets.streetid
        AND DATE(incident_record.date) = %s
    GROUP BY streets.streetid, streets.geom;
""", (reference_date, reference_date))

Script 2 — Spatial snapping. Raw incident records arrive with latitude/longitude but no street identifier. This script snaps each unsnapped incident to its nearest street segment using PostGIS geography distance, capped at a 500-meter search radius. The work is batched — 200 updates committed at a time — so a partial failure doesn’t roll back the whole run.

cur.execute("""
    SELECT streetid,
           ST_Distance(
               ST_SetSRID(ST_Point(%s, %s), 4326)::geography,
               geom::geography
           ) AS distance
    FROM chicagostreetsfinal_wgs84
    WHERE ST_DWithin(
        ST_SetSRID(ST_Point(%s, %s), 4326)::geography,
        geom::geography,
        500
    )
    ORDER BY distance ASC
    LIMIT 1;
""", (lon, lat, lon, lat))

Script 3 — Street-level prediction. A RandomForestRegressor trains on the aggregated daily incident counts per street and produces a predicted count for each segment. Predictions are written back into a predicted_crime table with a spatial geometry column, so GeoServer can serve them as a layer without any additional processing.

aggregated_df = crime_df.groupby("streetid").agg(
    total_incident_count=("incident_count", "sum"),
    avg_daily_incident=("incident_count", "mean"),
    incident_days=("incident_count", "count"),
    avg_weekend_incident=("is_weekend", "mean")
).reset_index()

model = RandomForestRegressor(n_estimators=100, random_state=42)
model.fit(X_train, y_train)

aggregated_df["predicted_incident_count"] = model.predict(
    scaler.transform(features)
)

The prediction is not the point — the pipeline that produces it is. Any model could be substituted here. What matters is that the pipeline runs end to end, refreshes on schedule, and writes back into a spatial table that the front-end can render without additional glue.

The Dashboard

The interface is designed around a single principle: the map is the first-class citizen, and every other panel is a lens on the same data.

Map — Current and Predicted, Side by Side

The centerpiece is a split view. On the left, the current observed distribution as a heatmap over the street network. On the right, the predicted distribution for the same streets. Both panels share a base map and camera state, so panning one pans the other.

The comparison is the reason the dashboard exists. Numbers in a table tell you that a street had more incidents yesterday than the day before. Side-by-side maps tell you where and how the pattern changes — which streets concentrate, which diffuse, which patterns hold across the prediction boundary and which don’t.

Hourly Clock

A polar chart in the top-right corner shows the distribution of incidents across the 24-hour cycle. The shape of this distribution is one of the most informative things about urban incident data — different neighborhoods have different peak hours, and the pattern correlates strongly with land use, transit access, and commercial activity.

Weekly Calendar Heatmap

A month-at-a-glance calendar view, laid out with days on the Y-axis and weeks on the X-axis, with each cell shaded by incident count. This view answers questions that scalar summaries can’t: is there a weekend effect? A midweek spike? A seasonal drift?

Top Incident Types

A horizontal stacked bar chart showing the top three incident categories by community area, ordered by frequency. This gives an immediate sense of what kinds of events dominate which parts of the city — one area might be dominated by a single category, another might show a long tail.

Historical Trend

A bar chart of incident counts by year, spanning the full available history. This is the context view — any single day’s snapshot only makes sense against the multi-year baseline.

Dynamic Filtering

All panels react to a shared filter state. Selecting a community area, adjusting the date range, or toggling an incident-type filter propagates through every visualization. There’s no separate “apply” button — the state is reactive.

Why Street Level

Most urban dashboards operate at the community-area or census-tract scale. That granularity is useful for aggregate reporting but too coarse for the questions that actually drive intervention decisions.

Street-level granularity is different. It answers questions like:

  • Which specific segments are consistently hot, versus which are transient?
  • Do incident clusters concentrate on arterials or on side streets?
  • How does the pattern change at intersections versus mid-block?
  • Does a 50-meter buffer around a transit stop show a different profile than a 50-meter buffer around a school?

None of these questions are answerable at tract scale. They require the analysis to be performed on the street network itself — which means the entire stack has to support vector street geometry from storage through serving to rendering. That’s the architectural choice this project makes, and it’s the reason the pipeline is built on PostGIS vector operations rather than raster grids.

What’s Under the Hood

Storage

  • PostgreSQL 15 + PostGIS 3.x
  • Separate spatial indexes on street geometry and incident geometry
  • Idempotent derived tables refreshed on schedule

Serving

  • GeoServer 2.x with WMS and WFS endpoints
  • Cached tiles for base layers, dynamic WFS for filtered views

Application

  • Django 4.x backend
  • Scheduled Python scripts for pipeline refresh
  • REST API for filter state and incident count queries

Front-end

  • OpenLayers 7 for map rendering
  • D3 v7 for the polar clock, calendar heatmap, and bar charts
  • Custom JavaScript for filter orchestration
  • No framework overhead — the map viewport is the only heavy DOM element

Project Scope

The system was built as a semester project for a WebGIS course — the constraints were real, and the scope reflects that. Some things that a production deployment would need are not present:

  • Authentication. No user accounts or role-based access. A production version would need at least an analyst/admin split.
  • Streaming. The pipeline runs on a schedule. Real-time ingestion from a live feed is possible but not implemented.
  • Model validation. The RandomForest predictor is a demonstration of the pipeline, not a tuned model. A production version would need proper spatial cross-validation, feature engineering, and backtesting against held-out history.
  • Performance at city scale. The dashboard handles Chicago comfortably. Scaling to multiple cities would require a more sophisticated caching layer and possibly a vector-tile pipeline instead of WFS.

None of these are fundamental limitations of the architecture — they’re the practical scope boundaries of a semester project.

What This Project Demonstrates

Beyond the specific dashboard, the project is a demonstration of end-to-end spatial systems thinking:

Data infrastructure. A working PostGIS schema with proper spatial indexing, spatial joins, and derived-table scheduling. The pipeline runs unattended and produces deterministic outputs.

Service architecture. A layered design where each component has one job and one clear interface. GeoServer doesn’t know about Django; Django doesn’t know about OpenLayers. Each layer can be replaced independently.

Front-end integration. Multiple visualization techniques — map, polar chart, calendar heatmap, bar chart, line chart — all orchestrated through a shared filter state. The user interacts with one control and every panel updates coherently.

Street-level spatial reasoning. Every spatial operation in the pipeline works on vector street geometry, not raster grids. This is the harder path, and it’s the one that produces results at a resolution that actually supports intervention decisions.
